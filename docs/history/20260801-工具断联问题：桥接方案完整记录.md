# 工具断联问题：桥接方案完整记录

> **创建时间**：2026-08-01
> **核心关键词**：工具断联、tools-bridge、桥接方案、globals.d.ts、级联依赖、ToolUseContext

---

## 一、问题发现

### 背景

Phase 0-6 将 Claude Code 源码从 1907 文件/512K 行削减到 480 文件/154K 行（-70%）。Phase 7-11 修复了基础类型系统和 MCP 服务层，`npx tsc` 项目级编译零错误。

但主入口 `main.ts` 使用的是 3 个手写工具（Bash/Read/Write），保留了作为参考源码的 10 个 Claude Code 原生工具文件（BashTool/、FileReadTool/ 等）。工具文件和主入口之间**没有 import 关系**——两者物理同目录、逻辑隔离。

### 触发

尝试在 `main.ts` 中添加 `import { getAllBaseTools } from './tools.js'` 以证明工具系统连通性。编译立即报错——`tsconfig.json` 的 `include: ["src/main.ts"]` 原本只检查 main.ts 的单文件依赖树。一旦 import `tools.ts`，TypeScript 会递归解析所有 10 个工具的 import，触发级联依赖断裂。

展开 tsconfig 到 `src/**/*.ts` 后，错误暴增至 **2600 个**。

---

## 二、根因分析

### 错误分类（2600 个错误）

| 错误类型 | 数量 | 根因 |
|---------|------|------|
| `Cannot find module 'bun:bundle'` | 38 | Anthropic 专有构建时宏，外部环境不存在 |
| `Cannot find module '../bootstrap/state.js'` | 60 | Phase 2/3 删除的状态管理模块 |
| `Cannot find name 'MACRO'` | 68 | Anthropic 构建时注入的版本宏，外部不存在 |
| `Cannot find name 'AnalyticsMetadata_...'` | 65 | Phase 1 删除的遥测类型 |
| `Property 'getAppState' does not exist on type 'ToolUseContext'` | 61 | Phase 3 精简 ToolUseContext 时删除了 UI 相关属性 |
| `Cannot use namespace 'Message' as a type` | 34 | types/message 被删除 |
| `Cannot find module 'lodash-es/memoize.js'` | 多种 | Phase 0 未安装 lodash-es 类型 |
| 其他（JSX、implicit any、strict null） | ~2200 | UI/React 代码残留、strict 模式兼容 |

### 根本原因

**不是某个文件的问题，是系统性的。** 10 个工具文件中嵌入了对整个 Claude Code 运行时环境的深层依赖——全局状态（AppState）、权限管线（permissions/）、遥测（analytics/）、UI 渲染（components/）、Anthropic 专有构建宏（bun:bundle、MACRO）。删除这些模块时，我们只删了目录，没有修改保留文件中对它们的引用。2600 个错误是这一决策的累积结果。

---

## 三、解决方案探索

### 尝试一：逐文件修复（放弃）

逐一修复 10 个工具的 import，创建 stub 文件替代已删除模块。

**结果**：创建了 10+ 个 stub 文件（services/analytics/、services/lsp/、utils/permissions/ 等），安装了 lodash-es 和 p-map，修复了 Tool.ts 的类型导出。错误从 2600 降到 2041，但陷入 whack-a-mole——每修复一个模块暴露更多深层依赖。

**放弃原因**：10 个工具的总依赖深度远超预期。BashTool 单文件 295 个 import/export，FileReadTool 引用 memdir/（记忆目录）、image-processor-napi（图像处理）、sharp（图片库）。完整修复需要重建 ~50% 的 Claude Code 运行时——抵消了 Phase 0-6 的削减成果。

### 尝试二：globals.d.ts 全局声明（部分成功）

创建 `src/globals.d.ts`，用 TypeScript ambient module declaration 批量声明 60+ 个已删除模块。

**结果**：错误从 2041 降到 ~1500，但遇到了类型不兼容的新问题——Message 类型（我们 stub 的是 `{role, content}`，但原代码期望的是一个包含 `type`、`uuid`、`message` 等几十个属性的判别联合类型）。修复类型兼容需要逐文件理解原代码的类型语义。

**结论**：globals.d.ts 可以解决"模块不存在"的问题（TS2307），但无法解决"类型不匹配"的问题。后者需要深度理解每个调用点的预期类型。

### 尝试三：tools-bridge.ts 桥接层（采用）

**核心思想**：不修复原工具文件，而是建一个**新的桥接层**，暴露与原工具系统相同的接口（name/description/inputSchema + execute），内部用纯 Node.js 标准库实现。

**架构**：

```
main.ts
  ├── import { ALL_TOOLS } from './tools-bridge.js'
  │     → 10个工具的 JSON Schema（给 LLM 看）
  └── import { executeTool } from './tools-bridge.js'
        → 根据 tool name 分发到对应实现

tools-bridge.ts  ← 零断裂 import，只依赖 Node.js 标准库
  ├── Bash: execSync
  ├── Read: readFileSync (带行号)
  ├── Write: writeFileSync
  ├── Edit: readFileSync → replace → writeFileSync
  ├── Glob: execSync find
  ├── Grep: execSync grep
  ├── WebSearch: (stub — 调外部 API)
  ├── WebFetch: (stub — fetch)
  ├── Task: (stub — 本地记录)
  └── MCP: (stub — 外部 MCP)
```

**tsconfig**：`include: ["src/main.ts", "src/tools-bridge.ts"]`——只检查两个文件，其余 478 个文件不作为编译目标，但保留在目录中作为参考源码。

## 四、最终方案：桥接层 + 全局声明 + 限制编译范围

### 架构总览

```
                    ┌─────────────────────────────┐
                    │        main.ts (220行)       │
                    │   LLM循环 + CLI + provider   │
                    └──────────┬──────────────────┘
                               │ import
                    ┌──────────▼──────────────────┐
                    │   tools-bridge.ts (230行)    │
                    │   ALL_TOOLS + executeTool()  │
                    │   零断裂依赖，纯标准库       │
                    └─────────────────────────────┘
                    
                    ┌─────────────────────────────┐
                    │   src/tools/ (10个目录)       │
                    │   BashTool/ FileReadTool/ ... │
                    │   参考源码 — import断裂       │
                    │   可 import 但不可独立编译    │
                    └─────────────────────────────┘
                              ↑ 修复声明
                    ┌─────────────────────────────┐
                    │   globals.d.ts               │
                    │   60+ ambient module 声明    │
                    │   MACRO/Bun/JSX 全局类型      │
                    └─────────────────────────────┘
                    
                    ┌─────────────────────────────┐
                    │   tsconfig.json              │
                    │   include: [main.ts, bridge] │
                    │   仅2文件编译，其余参考       │
                    └─────────────────────────────┘
```

### 验证

```

node dist/main.js (DeepSeek)     → 正常响应，10 tools，2684ms
```

## 五、桥接方案 vs 原生工具——差异分析

### 5.1 当前桥接层缺少的能力

| 原生工具能力 | 桥接层状态 | 影响 |
|------------|-----------|------|
| **Bash 安全沙箱** (Bubblewrap/Seatbelt) | ❌ 未实现 | 命令直接执行，无 OS 级隔离。自己用安全，开放给他人有风险 |
| **Bash 权限检查** (30+ 安全校验) | ❌ 未实现 | 无注入检测、无危险命令拦截 |
| **Bash 后台执行** (run_in_background) | ❌ 未实现 | 不支持长时间任务、流式输出 |
| **FileRead 图片处理** (sharp) | ❌ 未实现 | 无法读取图片内容 |
| **FileRead PDF 解析** | ❌ 未实现 | 无法解析 PDF |
| **FileRead 文件大小限制** (limits.ts) | ❌ 未实现 | 大文件无截断保护 |
| **FileEdit diff 生成** | ❌ 未实现 | 编辑后无差异对比 |
| **FileEdit 撤销支持** | ❌ 未实现 | 无法回滚编辑 |
| **Glob/Grep ignore 规则** (.gitignore) | ❌ 未实现 | 会搜索 node_modules/.git 等目录 |
| **WebSearch 真实搜索** | ❌ 未实现 | stub 返回提示信息 |
| **WebFetch 真实抓取** | ❌ 未实现 | stub 返回提示信息 |
| **MCP 协议** | ❌ 未实现 | 无法连接外部 MCP Server |
| **Task 持久化** | ❌ 未实现 | 任务不跨会话保存 |

### 5.2 架构差异

| 维度 | 原生工具 | 桥接层 |
|------|---------|--------|
| **类型系统** | Zod Schema → 自动校验输入 | TypeScript interface → 手动校验 |
| **执行模型** | 9 阶段管道（validateInput→checkPermissions→PreToolUse hooks→call→PostToolUse hooks） | 单函数直接执行 |
| **错误处理** | ToolResult<T> — 结构化错误 + 上下文修改 | ToolResult {content, error} — 简单字符串 |
| **权限** | 14 步权限决策 + Hook 系统 | 无权限控制 |
| **可观测性** | 每步有遥测埋点 | 无 |
| **Prompt 注入** | tool.prompt() 动态生成工具使用说明 | 静态 description 字符串 |

### 5.3 关键架构决策：为什么桥接而不是修复

| 决策 | 理由 |
|------|------|
| **不修复原生工具** | 10 个工具的级联依赖需要重建 ~50% Claude Code 运行时。这不是修 bug，是在重建一个框架。 |
| **桥接层独立实现** | 230 行代码实现了 LLM 可用的全部 10 个工具接口。后续如果要接入原生工具，桥接层就是适配层——改 executeTool 的分发逻辑即可。 |
| **原生工具保留为参考** | 当需要某个原生工具的高级能力时（如 BashTool 的安全沙箱），可以直接读源码理解实现，然后在桥接层中按需实现。 |
| **tsconfig 限制编译范围** | 避免 2600 个历史错误的噪音。想接入哪个工具，把它加到 include 列表，逐个修复它的依赖。 |

## 六、桥接方案的优缺点

### 优点

1. **零依赖断裂**：只依赖 Node.js 标准库（fs、child_process、path），不 import 任何原生工具文件
2. **编译速度快**：只检查 2 个文件，vs 全量 480 个文件
3. **新增工具成本低**：在 ALL_TOOLS 数组中加一个条目 + executeTool 的 case 分支
4. **渐进式接入**：保留原生工具源码。想接入 BashTool 的安全沙箱？把 BashTool/ 的依赖修好，然后在 executeTool 的 Bash case 里替换实现
5. **多 provider 兼容**：ALL_TOOLS 的 JSON Schema 格式同时兼容 Anthropic 和 OpenAI
6. **已通过实际验证**：DeepSeek V4 Pro 上正常运行

### 缺点

1. **缺少安全层**：无沙箱、无注入检测、无权限控制。当前只适合个人使用
2. **功能不完整**：WebSearch/WebFetch/MCP 三个工具是 stub
3. **不是"真正的工具系统"**：没有 ToolUseContext、没有 Zod 校验、没有 9 阶段管道。LLM 传入错误参数时可能直接崩溃
4. **Schema 与实现分离**：ALL_TOOLS 的 Schema 是手写的，不和 executeTool 的实现自动同步。原生工具的 Schema 是从 Zod 类型自动生成的，能保证一致性
5. **维护成本**：如果 Anthropic/OpenAI 更新了 Function Calling 协议，需要手动同步 TOOLS_ANTHROPIC/TOOLS_OPENAI 的格式转换

### 适用场景

✅ **适合**：个人开发、本地使用、快速原型、学习研究
⚠️ **部分适合**：小团队内部分享（需自己加权限控制）
❌ **不适合**：生产环境、多用户 SaaS、需要完整安全审计的场景

## 七、后续升级路径

当需要原生工具的某个能力时，按以下顺序升级：

```
1. 在桥接层手写实现（如 Edit 工具的 diff 生成）
2. 如果实现太复杂 → 读原生工具源码，提取核心逻辑
3. 如果需要完整工具 → 修复该工具的级联依赖，替换桥接层的对应 case
```

当前状态：v0.2.0，桥接方案，10 工具，DeepSeek 验证通过。
