## 二、根因分析

### 2.1 为什么 1 GB 泄露造成 28 GB swap

直觉上 1 GB / 16 GB RAM = 6%，不应该拖垮系统。但关键不是"占多少内存"，而是 **"CPU 在干什么"**：

```
feishu MCP: while(true) { poll_api(); process_events(); }  // 99.8% CPU

  ① feishu 抢 CPU → 正常应用被延迟
  ② feishu 不断触碰内存页 → 这些页无法 swap out
  ③ 系统为 feishu 腾地方 → 正常应用的内存页被 swap out
  ④ 正常应用需要时 → swap in → 又有新页被挤出
  ⑤ CPU 同时处理：用户工作 + feishu 死循环 + swap 压缩 = 三重负载

  结果：28 GB 不是"同时换出"，是 11 天里持续颠簸的累积总量
```

### 2.2 npx 子进程为什么不会自动退出

`npx` 拉起的进程是独立进程，不受父进程 `SIGTERM` 影响。父进程（Claude Code / shell）退出后，子进程继续运行直到系统重启或手动 kill。

```
正常：terminal → node main.js → child (随父退出)
npx： terminal → npm exec → feishu-plugin (独立！terminal 退出后继续跑)
```

### 2.3 ollama 为什么 kill 不死

ollama 通过 Homebrew 安装为 launchd 开机自启动服务。每次 `kill` 后 launchd 检测到进程退出，自动拉起新实例。

**正确做法**：
```bash
launchctl bootout gui/$(id -u)/homebrew.mxcl.ollama  # 卸载服务
brew uninstall ollama                                   # 卸载程序
rm -rf ~/.ollama                                        # 删除数据
rm ~/Library/LaunchAgents/homebrew.mxcl.ollama.plist   # 删除 plist
```

## 三、Phase 46 自保机制实战验证

Mycoder 在清理过程中尝试了 `pkill -f "Notion.app"`，被 Phase 46 的防御系统拦截：

```
Mycoder: pkill -f "Notion.app"
  ↓
PROCESS_MANAGEMENT_BLOCKED 第 1 层: /pkill/ 命中
  ↓
返回: BLOCKED: Unsafe process management — broadcast kill by name (pkill)
  ↓
Mycoder 自行调整: kill 12492 (精确 PID) ✅ 通过
```

**验证结论**：
- Phase 46 的全禁止 pkill 设计是正确的——不限于自引用，而是禁止 Agent 使用任何广播式杀进程
- Mycoder 被拦截后没有崩溃、没有绕过，而是正确地改用精确 PID
- 防御系统和 Agent 形成了有效的协作：规则拦 → Agent 理解 → 换安全方式

## 五、日常排查命令

```bash
# 按运行时间排序——僵尸排最前
ps aux --sort=-time | head -15

# 找所有 npx 拉起的进程
ps aux | grep "_npx"

# 按内存占用排序
ps aux --sort=-%mem | head -10

# 查看 swap 使用
sysctl vm.swapusage

# 查看 launchd 自启动服务
ls ~/Library/LaunchAgents/

# 查看监听端口
lsof -iTCP -sTCP:LISTEN -P | grep -v "^com.apple"
```
