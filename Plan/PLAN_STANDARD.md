# 计划记录规范

> 每条规则必须遵守。主计划（MASTER_PLAN.md）除外——它是活的索引，不加时间戳。

---

## 一、文件夹命名

```
Plan/{YYYYMMDD-HHMM}-{计划简称}/
```

例：`Plan/20260806-1555-session-refactor-phase7/`

- **时间戳精确到分钟（必须）**。取计划文件夹创建时的本地时间，不是计划执行时间
- 计划简称用英文小写 + 连字符（中文场景可用中文简述）
- 每个计划独占一个文件夹
- 反例：`Plan/20260807-任务树精简/` — 缺了 HHMM，无法区分同一天内的多个计划

## 二、文件夹内容

```
20260806-1555-session-refactor-phase7/
  README.md           ← 必选。做什么、为什么做、预期结果
  plan.md             ← 必选。完整设计方案
  work-mode.md        ← 必选。修改后的预期工作方式（流程图+调用链+数据流）
  execution.md        ← 必选。执行步骤 + 监督方案 + Agent 布局
  review.md           ← 审查后生成。Agent 集群审查报告（审查通过后才能执行）
  risks.md            ← 可选。手动风险评估（复杂计划额外加）
  summary.md          ← 可选。完成后的复盘总结
  observations.md     ← 测试后追加。实际测试中观察到的现象（事实描述，不加判断）
  fix-plan.md         ← 根据观察追加。针对现象的修正计划
  fix-results.md      ← 修正后追加。改了什么 + 达到什么效果 + 和预期的差距 + 是否继续迭代
```

### 迭代修正三文件规范

**observations.md** — 测试后记录事实：

```
## 观察 1: {简述}
- 触发条件: 输入了什么 / 做了什么操作
- 现象: 实际发生了什么（日志、返回值、卡住、报错等）
- 频率: 每次都触发 / 偶尔 / 仅一次
```

**fix-plan.md** — 根据观察制定修正计划：

```
## 修正 1: {针对哪个观察}
- 根因: 为什么会发生
- 方案: 怎么改（文件 + 改动点）
- 影响: 改了之后会影响哪些其他模块
- 验收: 怎么验证修好了
```

**fix-results.md** — 修正完成后的分析：

```
## 修正 1 结果
- 做了什么: 具体改了哪个文件、哪几行
- 达到了什么效果: 修好了 / 部分修好 / 没修好
- 和预期的差距: 是否完全解决了观察到的现象
- 是否继续迭代: 是（跳转到 fix-plan 修正 2）/ 否（关闭）
```

### work-mode.md 规范

必须包含：
1. **当前工作方式**（一句话 + 简图）
2. **修改后的工作方式**（详细流程图，标注改动点）
3. **调用链变化**（改前 vs 改后，精确到函数和文件）
4. **数据流变化**（什么数据从哪里来、到哪里去、谁持有）

### review.md 规范（审查后生成）

必须包含两个维度的结果：
1. **缺陷分析** — 当前缺陷 + 新引入缺陷 + 降级路径 + 性能 + 单点故障
2. **模块协调性** — 调用链 + 数据流 + 信号链 + 接口冲突 + 死代码风险

每个问题标注严重度（高危/中危/低危）和修复建议。审查不通过 → 修改计划 → 重新审查。

## 三、README.md 模板

```markdown
# {计划简称}

> 创建时间：YYYY-MM-DD HH:MM
> 状态：规划中 / 进行中 / 已完成 / 已废弃

## 要做什么

一句话说清楚。

## 为什么做

当前问题是什么，不做会怎样。

## 预期结果

做完了是什么状态，怎么验证。

## 相关计划

- [Phase X](../其他计划文件夹/README.md)
```

## 四、主计划同步

每创建一个计划文件夹，必须在 `MASTER_PLAN.md` 中记录——放在"进行中"或"已完成"表中，带文件夹链接。

## 五、执行前审查（必做）

**每个计划在动手执行之前，必须用 Agent 集群并行审查。** 至少包含两个维度：

### 维度 1：缺陷分析

- 当前代码中存在的缺陷是什么？计划是否修复了它们？
- 计划本身有没有引入新的缺陷？单点故障？数据丢失窗口？死锁？
- 降级路径是否完整？每个新功能是否有 fallback？

### 维度 2：模块协调性与连接性

- 新增模块和现有模块之间的调用链是否完整？
- 数据流是否闭环（谁生产、谁消费、谁清理）？
- 信号是否在每个环节都被正确处理（生产→传递→消费→持久化）？
- 有没有"写了但没接上"的死代码风险？

### 审查方式

- 至少 2 个 Agent 并行，各负责一个维度
- 审查结果追加到计划文件夹的 `review.md`
- 审查不通过 → 修改计划 → 重新审查 → 通过后才能执行

---

## 六、历史计划

现有的零散 `.md` 文件暂时保留——逐步迁移到文件夹格式。新计划严格按本规范执行。
