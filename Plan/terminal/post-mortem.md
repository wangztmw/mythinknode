## 一、错误链条

### 第一步：把症状当根因（fix-plan.md）

**错误假设**：Terminal 崩溃是因为 Mycoder 输出总量太大、速率太高。需要从总量、速率、ANSI 复杂度、行宽四个维度全面控制。

**实际上**：总量和速率不是原因。Claude Code 也输出海量数据，不崩。根本原因只有一个——超长行。

**浪费了什么**：
- 四层魔法参数的详细设计（行宽 200、输出 4000、节流 16ms、突发 10KB/s）
- OutputThrottle 类的设计
- 80+ 行的实施计划

### 第二步：过度设计（terminal-technology.md）

**错误假设**：既然 scrollback 会撑爆 Terminal，那不如换个没有 scrollback 的屏幕（交替屏）。

**实际上**：不需要换屏幕。只需要确保不输出超长行。Claude Code 用主屏也不崩——因为它自动折行。

**浪费了什么**：
- B1/B2/B3/B4 四条技术路线的详细对比
- 交替屏的实施方案（~250 行代码的预估）
- 牺牲 scrollback 的代价分析（这个分析本身是对的，但针对的是不存在的问题）

### 第三步：过度抽象（corrected-fix.md）

**错误假设**：方向对了（折行），但实现上需要一个新的抽象层——`createWrappedWriter` 工厂函数、`OutputThrottle` 类、独立文件。

**实际上**：不需要任何抽象。直接 monkey-patch `process.stdout.write` 就行。30 行，零新文件。

**浪费了什么**：
- WrappedWriter 类的接口设计
- 新的 `src/terminal.ts` 文件规划
- resize 处理逻辑

### 第四步：对输入端过度反应（input-trigger.md）

**错误假设**：语音输入触发的崩溃是独立机制，需要独立修复（50ms 延迟 + 2000 字符限制）。

**实际上**：语音输入的崩溃机制和程序输出完全一样——都是超长行通过 PTY 进入 Terminal 的 SwiftUI 渲染管线。monkey-patch stdout/stderr 已经覆盖了所有路径——因为输入回显也是通过 PTY 写入 Terminal 的，而 `wrapOutput` 拦截的是写入端。**折行修复自动覆盖了输入端**，50ms 延迟和长度限制是多余的。

**浪费了什么**：
- 50ms 启动延迟的设计
- 输入长度限制的方案
- 输入队列的评估（虽然队列方案是用户提的，不是 AI 提的）

### 第五步：既有补丁的误导（ansi.ts:14）

```typescript
// 超长文本→纯文本(防止Terminal缓冲区溢出——macOS persistent UI内存bug)
if (text.length > 8000) return text.replace(...);
```

这个补丁在本次诊断之前就已经存在。它是之前为了解决 Terminal 崩溃问题加的。但它的假设是错的——它针对的是"文本总量太大"而不是"单行太宽"。**这个补丁的存在本身就是一个认知陷阱**：它让人觉得"我们已经处理了 Terminal 崩溃问题"，从而不再怀疑输出格式本身。

在正确修复（monkey-patch 折行）之后，这个补丁不再必要——但也不需要删除。它只是变得冗余了：折行已经保证了行宽安全，8000 字符阈值降级 ANSI 仍然能减少 Terminal 的渲染负载。**它从"主要防线"变成了"性能优化"。**

## 二、为什么走偏了

### 原因一：崩溃进程对不上

崩溃报告显示 `Process: Terminal [3510]`，不是 Mycoder。第一反应是"这是 Terminal 的 bug"。直到深入分析 SwiftUI 布局递归栈，才发现触发条件是 Mycoder 输出的超长行。

**教训**：崩溃进程 ≠ 责任进程。一个程序的输出可以让另一个程序崩溃。

### 原因二：对标对象选错了

一直在对比"为什么 npm install 不崩"，而不是对比"为什么 Claude Code 不崩"。npm install 的输出模式（短行、自限速）和 Mycoder（bursty、含超长行）完全没有可比性。Claude Code 才是正确的对标对象——它和 Mycoder 做同样的事（AI 编程 Agent），输出量同样大，但它不崩。

**教训**：找对标要找同类。Claude Code 不崩的原因（Ink/Yoga 自动折行）才是关键信息。这个信息在第四轮才被发现——太晚了。

### 原因三：在诊断完成前开始设计方案

第一轮拿到崩溃报告后，15 分钟内就开始写 fix-plan.md。没有先做足够的对比实验（比如：手动构造一个 300 字符的行写到 Terminal，看是否会崩）。如果先做这个实验，30 秒就能确认根因。

**教训**：设计之前先证伪。做一个最小可复现实验，验证根因假设，再写方案。

### 原因四：过度重视"完备性"

每一版方案都在追求"覆盖所有攻击面"——输出端、输入端、速率、总量、行宽、ANSI。这种追求在架构设计阶段是有价值的，但在 bug 修复阶段是负担。一个 bug 只需要一个 fix。把所有维度都列出来反而掩盖了真正需要修的那一个。

**教训**：修 bug 不要做架构设计。找到最小修复，实施，验证。

## 五、教训清单

1. **崩溃进程 ≠ 责任进程。** 先确认因果方向。
2. **找对标要找同类。** Claude Code 不崩 → 看它做了什么 Mycoder 没做 → 找到差异。
3. **先证伪，再设计。** 做一个最小复现实验，30 秒确认根因，再写方案。
4. **修 bug 不要做架构设计。** 找到最小修复，实施，验证。奥卡姆剃刀。
5. **警惕既有补丁的误导。** ansi.ts:14 的存在让人以为"这个问题已经处理过了"，关闭了进一步调查。
6. **用户的直觉值得信任。** 用户在第一轮就说"Terminal 容易崩"→ 第二轮说"会不会是输入也有问题"→ 第四轮说"魔法参数是绥靖"→ 第五轮说"Claude Code 不是交替屏"。每次纠正都让方向更接近真相。
7. **改 A 处代码前，问自己：A 改变了什么时序？什么资源依赖这个时序？** 改 cli.ts（事件驱动输入）导致 LLM 请求变密集，暴露了 HTTP keep-alive 连接池复用腐化的问题。终端 I/O 和网络 I/O 看起来毫无关系，通过"请求密度"这个隐变量耦合。（详见 Notion 案例：修复 Terminal 崩溃后偶发 API 断连）
