## 零、承认一个错误

之前的 `fix-plan.md` 列了四层输出控制：行宽限制（200字符）、输出上限（4000字符）、节流（16ms）、突发降级（10KB/s）。每层都有一个魔法数字。加起来 82 行代码。

**这套方案的本质是：承认 Terminal 会崩，然后小心翼翼地控制 Mycoder 的输出，希望不要踩到 Terminal 的崩溃阈值。**

这是绥靖。不是解决。

真正的问题是：**Mycoder 为 Agent 选择了正确的抽象（分离引擎和渲染），但在终端渲染层选择了错误的实现技术（`console.log` + `process.stderr.write` → 无限增长的 scrollback）。** 这个技术选择，在任何高吞吐场景下都会出问题。

## 一、当前技术栈的致命假设

```
Mycoder
  ├── console.log      → stdout → PTY → Terminal scrollback (无限增长)
  └── stderr.write     → stderr → PTY → Terminal scrollback (无限增长)
```

`console.log` 和 `stderr.write` 底层都是 `fs.writeSync(fd, buffer)` —— 往文件描述符写字节。PTY 把这些字节原样传给 Terminal。Terminal 把它们**永久追加**到 scrollback buffer。

这个模型有两个致命假设：
1. **输出量是有限的** —— 一个 CLI 工具执行一次，打印结果，退出。输出 50 行还是 500 行都无所谓。
2. **输出速率是自限的** —— 程序的输出速率自然受限于它的计算/IO（编译、下载、安装）。

Mycoder 打破了这两个假设：
1. **输出量是无限的** —— 25 轮迭代 × 无限工具调用 × 无限 LLM 回复。一次对话可以产生几万行输出。
2. **输出速率是突发式的** —— LLM 返回瞬间 5000 字符，然后工具调用瞬间 1000 字符。burst → 静默 → burst → 静默。

**用 scrollback 终端做 Agent 界面，就像用 `tail -f /dev/zero` 当桌面背景。** 内容无限增长，渲染引擎最终会崩。

## 二、三条路线

| 路线 | 核心思路 | 例子 | 复杂度 |
|------|---------|------|--------|
| A | 留在当前技术栈，加防御参数 | `fix-plan.md`（已被否定） | 低 |
| B | 替换终端渲染技术 | 见下方详述 | 中 |
| C | 绕过终端，用其他 UI | Web UI、GUI | 高 |

路线 A 已放弃。路线 C（Web UI）是另一个大工程，暂不展开。聚焦路线 B：**在终端内，换一种终端渲染技术。**

### 路线 B 的四个选项

| 选项 | 技术 | 代表作 | 核心机制 |
|------|------|--------|---------|
| **B1** | 交替屏幕缓冲区 | vim, less, htop, tmux | 切换到一个独立的屏幕，退出时恢复原屏 |
| **B2** | 有限区域 + 手动滚动 | 自建 viewport | 在终端上维护一个固定大小的"窗口"，内容超出时用方向键翻页 |
| **B3** | REPL + Pager 组合 | `git diff` + `less` | 长输出自动 pipe 到 pager |
| **B4** | 日志分离 | 很多服务器 | 终端只显示摘要，详细内容写文件 |

## 三、B1：交替屏幕缓冲区（推荐）

### 原理

每个终端支持两个屏幕缓冲区：
- **主屏（main screen）**：正常使用时的屏幕。内容进入 scrollback。
- **交替屏（alternate screen）**：程序切换进去的独立屏幕。**没有 scrollback**。程序退出后恢复主屏，交替屏内容消失。

```bash
# 切换进交替屏
$ echo -e '\x1b[?1049h'
# 此时终端清屏，进入一个独立空间
# 程序可以自由写入任何内容
# 退出交替屏
$ echo -e '\x1b[?1049l'
# 主屏恢复，原来的内容还在
```

这是 ANSI 标准的一部分（`\x1b[?1049h` / `\x1b[?1049l`），所有现代终端都支持。

### 为什么这个方案是治本的

交替屏**没有 scrollback**。Mycoder 写入的所有内容，只在交替屏上显示。Terminal 不需要维护一个无限增长的文本缓冲区。内容满了屏幕高度后就从顶部滚出去——这是屏幕级别的滚动（overwrite），不是 scrollback 级别的追加（append）。

**Apple Terminal 的 SwiftUI 渲染在交替屏模式下的行为完全不同**：它只需要渲染**一屏的内容**（~40-50 行），而不是 108MB 的 scrollback 历史。文本视图的 intrinsic size 始终是固定的（= 屏幕尺寸），不会触发布局递归。

### 代价：失去原生 scrollback

交替屏没有 scrollback。用户不能像正常终端那样用鼠标滚轮回看之前的输出。如果要支持"回看历史"，Mycoder 需要自己实现一个简易的滚动模式——类似 `less` 的做法。

这听起来是额外工作量，但其实可控：
- Mycoder 已经在内存中保存了 `sessionMessages`（完整的对话历史）
- 给 Mycoder 加一个 `/history` 命令，切到一个浏览模式
- 或者简单地把完整对话写到一个日志文件（`~/.mycoder/sessions/`），用户想看历史时用 `less` 打开

### 实现方案

交替屏幕只需要在程序启动和退出时各发一个转义序列。不需要任何库依赖：

```typescript
// 进入交替屏
process.stdout.write('\x1b[?1049h');
// 隐藏光标
process.stdout.write('\x1b[?25l');

// === Agent 主循环 ===

// 退出交替屏
process.stdout.write('\x1b[?25h');  // 显示光标
process.stdout.write('\x1b[?1049l'); // 恢复主屏
```

加上 ANSI 光标控制（移动光标到指定位置、清除行、清除屏幕），Mycoder 可以：
- 在屏幕顶部显示对话（可滚动）
- 在屏幕底部显示 tool call 状态
- 不在屏幕上累积无限内容

### 与当前架构的兼容性

Phase 50 已经把引擎和渲染分离了（`agent.ts` → `AgentResult { text, ms }`，`cli.ts` → `renderProgress`）。这个分离是正确的前提。现在只需要把 `cli.ts` 的渲染实现从"追加式 scrollback"改为"交替屏 + 光标控制"。

引擎层（`agent.ts`）完全不需要改动。

### 风险

1. **Windows 兼容性**：Windows Terminal 和 ConEmu 支持交替屏，但老版 cmd.exe 不支持。Mycoder 的目标用户用 macOS/Linux，风险可控。
2. **程序崩溃后交替屏残留**：如果 Mycoder 崩了没来得及发 `\x1b[?1049l`，用户的终端会留在交替屏里（显示 Mycoder 的最后画面）。用户体验类似于 vim 崩了——需要手动 `reset`。解决方案：注册 `process.on('exit')` 和 `SIGINT/SIGTERM` handler 确保恢复。

## 四、B2：有限区域 + 手动滚动

### 原理

不切交替屏，但在主屏上用 ANSI 光标控制维护一个固定大小的"显示窗口"。Mycoder 自己管理滚动——追踪当前显示到哪一行，超出窗口高度就把旧行滚出去（用 ANSI scroll region）。

### 与 B1 的区别

B1 = 让终端给一个全新的、没有 scrollback 的屏幕。
B2 = 在主屏上，用 ANSI 码手工模拟同样的效果。

### 为什么不如 B1

- B1 是终端原生支持的，退出后自动恢复。B2 需要自己处理 resize、信号、各种边界情况。
- B2 仍然在主屏上，如果实现有 bug 可能污染用户的 scrollback。
- B1 只需要 2 个转义序列。B2 需要几十个。

**B1 是更好的 B2。**

## 五、B3：REPL + Pager 组合

### 原理

正常 REPL 交互，但当单次输出超过一定行数时，自动 pipe 到 `less`（或内置 pager）。类似 `git diff` 的行为。

### 为什么不适合 Mycoder

Mycoder 的交互模式不是"一次命令 → 一次输出"——它是**连续的**。Agent 在 25 轮迭代中不断输出 tool call 状态，用户需要**实时看到**这些输出。Pager 会阻断这个流程——每次 tool call 都要等用户按 `q` 才能继续。

pager 适合"一次性输出"的场景。不适合"持续流式输出"的场景。

---

## 六、B4：日志分离

### 原理

终端只显示精简摘要（"Agent is thinking...", "3 tools executed", "Done. Full log: ~/.mycoder/logs/2026-08-03.md"），详细内容全部写文件。

### 为什么不够

用户需要在对话过程中看到 tool call 的输出——不是为了存档，是为了**理解 Agent 在做什么、是否走偏、是否需要 Task(direct) 干预**。如果把细节都藏到日志文件里，用户失去了对 Agent 的实时感知。

B4 可以作为**补充**（完整对话日志始终写文件），但不能作为**替代**。

## 七、推荐方案：B1（交替屏）+ B4（日志备份）

### 架构

```
Mycoder
  ├── agent.ts          引擎层（不变）
  │   └── AgentResult { text, ms }
  │
  ├── cli.ts            渲染层（改）
  │   ├── 交替屏模式：所有输出写到一个固定大小的屏幕缓冲区
  │   ├── 顶部 3/4：对话内容（自动滚动，类似聊天）
  │   ├── 底部 1/4：工具调用状态（实时更新）
  │   └── 退出时：恢复主屏
  │
  └── session log       日志层（新增）
      └── ~/.mycoder/sessions/2026-08-03-143052.md
          完整对话记录（全量，不受终端限制）
```

### 为什么这个方案不依赖魔法参数

| 之前的问题 | 交替屏如何从根本上解决 |
|-----------|---------------------|
| 需要行宽上限（200 字符） | 不需要——交替屏宽度 = 终端宽度，超宽行自动折行是终端的正常行为，不再触发布局递归 |
| 需要输出总量上限（4000 字符） | 不需要——交替屏只有 N 行高度，旧内容自然滚出屏幕，不累积到 scrollback |
| 需要速率节流（16ms） | 不需要——屏幕只有 40-50 行，每次渲染 O(50) 而非 O(100000) |
| 需要突发降级（10KB/s） | 不需要——同上 |
| 需要 50ms 输入延迟 | 不需要——交替屏的渲染负载是常数，不会因为输入回显叠加输出而翻倍 |

**交替屏改变了问题的量级**：从"管理无限增长的 scrollback"变成"渲染固定大小的屏幕"。前者需要魔法参数来控制增长速度。后者是常数复杂度，不需要参数。

### 用户体验的变化

| 场景 | 之前 | 之后 |
|------|------|------|
| Agent 对话过程中 | 输出追加到 scrollback，鼠标可回滚 | 输出显示在交替屏上，旧内容自动滚出屏幕 |
| 想看之前的输出 | 鼠标滚轮往上滚 | `/history` 命令打开浏览模式，或打开日志文件 |
| 对话结束，退出 Mycoder | scrollback 保留在 Terminal 里 | 屏幕恢复，所有输出记录在 `~/.mycoder/sessions/` |
| 使用 ctrl+c 中断 | 交替屏可能残留 | `process.on('SIGINT')` 恢复主屏 |

### 实现规模

B1 不是重写。是一个有限范围的改动：
- `cli.ts`：约 100-150 行重写（当前 101 行）
- 新增 `src/terminal.ts`：约 80-100 行（交替屏管理 + ANSI 光标控制工具函数）
- 新增 session 日志写入：约 20 行
- `ansi.ts`：保留，但简化（不再需要行宽限制和突发降级逻辑）

总计约 200-250 行净增。比之前四层防御（82 行）多，但**换来的是一劳永逸**。

## 八、如果还不行——从底层确认是否是 Terminal 的问题

交替屏方案解决的是"Mycoder 输出太多导致 Terminal 渲染管线崩溃"。但如果交替屏模式下 Terminal 仍然崩，那就不是输出量的问题——是 **macOS Terminal.app 本身在 PTY + SwiftUI 实现上有 bug，任何高吞吐的 PTY 流量都可能触发它。**

这种情况下：
1. 验证方式：用 `yes` 命令在交替屏中跑，看 Terminal 是否崩
2. 如果崩：这是 Apple 的 bug，Mycoder 能做的已经做到位了
3. 建议用户换终端模拟器（iTerm2、kitty、WezTerm 都不是 SwiftUI 写的，不存在这个崩溃路径）

**交替屏方案是 Mycoder 能做的最好努力。如果交替屏下 Terminal 还崩，责任的边界就在 Apple 那边了。**

## 九、总结

| 问题 | 绥靖方案 | 治本方案 |
|------|---------|---------|
| 本质 | 控制输出，别踩 Terminal 的崩溃阈值 | 换一种终端渲染技术，让崩溃阈值不再存在 |
| 手段 | 魔法参数：行宽/总量/速率/突发 | 交替屏：固定大小的渲染面 |
| 复杂度 | O(N)，N = scrollback 长度 | O(1)，只渲染一屏 |
| 代价 | 每个参数都可能不准确，需要反复调 | 用户失去原生 scrollback（用日志文件弥补） |
| 代码量 | 82 行 | ~250 行 |

**推荐路线**：B1（交替屏）+ B4（日志备份）。不改引擎层（agent.ts），只改渲染层（cli.ts）+ 新增终端控制（terminal.ts）。
