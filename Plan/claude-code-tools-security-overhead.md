# Claude Code 工具系统的安全权重备忘录

> **创建时间**：2026-08-02
> **核心论点**：Claude Code 工具层代码中，安全/权限/沙箱占了绝大部分体积。真正的工具逻辑本身很简洁。

## 一、核心数据：工具代码 ≠ 工具逻辑

Claude Code 的工具层有 **184 个文件 / 50,828 行代码**，分布在 36 个工具中。但拆开看每个工具的内部组成，**安全基础设施占据了不成比例的体积**。

### 1.1 按工具拆解

| 工具 | 文件数 | 总行数 | 安全相关行数 | 安全占比 | 安全组件 |
|------|--------|--------|-------------|----------|----------|
| **BashTool** | 18 | 12,411 | ~9,000 | **73%** | 沙箱适配(997L) + 权限检查(14步) + Haiku分类器 + Bash AST安全解析(7,621L) + 危险模式检测 |
| **PowerShellTool** | 14 | 8,959 | ~6,500 | **73%** | Windows 对应物，同样的安全架构 |
| **AgentTool** | 20 | 6,782 | ~1,500 | 22% | 子Agent权限继承 + 沙箱 + 工具白名单 |
| **FileEditTool** | 6 | 1,812 | ~600 | 33% | 路径边界检查 + diff备份 + 权限校验 |
| **FileReadTool** | 5 | 1,602 | ~400 | 25% | 二进制检测 + 大小限制 + 路径范围校验 |
| **FileWriteTool** | 3 | 856 | ~350 | 41% | 路径边界检查 + 原子写入 + 覆盖保护 |
| **WebFetchTool** | 5 | 1,131 | ~200 | 18% | URL白名单 + 域名校验 + 内容过滤 |
| **WebSearchTool** | 3 | 569 | ~100 | 18% | 域名白名单 |
| 其余 28 个工具 | ~110 | ~16,706 | ~3,000 | 18% | 各类权限/校验/边界检查 |

### 1.2 安全的总重量

```
工具层总代码:        50,828 行  (100%)
├── 安全基础设施:    ~21,650 行  (43%)   ← 权限+沙箱+AST解析+分类器+校验
├── 工具核心逻辑:    ~12,700 行  (25%)   ← 真正干活的部分
└── 其他(UI/序列化等): ~16,478 行  (32%)

仅 BashTool 一个工具:
├── 安全层:          ~9,000 行  (73%)   ← 沙箱+Bash AST+权限+分类器
└── 命令执行逻辑:    ~3,400 行  (27%)   ← 实际 execSync 就那么几行
```

**核心发现：工具层将近一半的代码不是在"做事情"，而是在"判断能不能做、做了会不会出事、出事了怎么拦住"。**

## 二、安全架构全景：四层 + 一管

Claude Code 的安全不是单一机制，而是**四层叠加 + 一条管道**。其中大部分代码在 `utils/` 而非 `tools/` 里，但它们是工具执行的必经路径。

### 2.1 四层安全体系

```
┌─────────────────────────────────────────────────────┐
│  第四层：行为层 (Hooks)                               │
│  utils/hooks/ — 17文件, 3,721行                     │
│  PreToolUse / PostToolUse / Notification / SessionStart│
│  用户自定义脚本干预工具调用                              │
├─────────────────────────────────────────────────────┤
│  第三层：隔离层 (Sandbox)                             │
│  utils/sandbox/ — ~1,000行 + @anthropic-ai/sandbox-runtime│
│  Bubblewrap(Linux) / Seatbelt(macOS)                 │
│  每次Bash命令外面包一层内核级隔离                        │
├─────────────────────────────────────────────────────┤
│  第二层：规则层 (Permissions)                          │
│  utils/permissions/ — 24文件, 9,409行                │
│  14步权限决策管线 + 规则匹配引擎 + YOLO分类器           │
│  allow/deny/ask 三级决策 + deny优先                   │
├─────────────────────────────────────────────────────┤
│  第一层：语法层 (Bash Parser)                          │
│  utils/bash/ — 23文件, 12,306行                      │
│  纯 TS Bash AST 解析器 + FAIL-CLOSED 安全分析          │
│  不认识的语法结构 → 标记 too-complex → 强制确认          │
└─────────────────────────────────────────────────────┘
```

### 2.2 一条管道：9 阶段工具执行

工具不是直接调用的，而是穿过 9 个阶段的管道：

```
用户输入 → [1.校验] → [2.权限检查] → [3.Hooks(Pre)] → [4.分类器(Haiku)] 
→ [5.沙箱包装] → [6.执行] → [7.结果校验] → [8.Hooks(Post)] → [9.回调] → 返回
```

每个阶段都可能拦截、修改或拒绝这次工具调用。my-coder 把这 9 阶段压成了 1 步：`tool.call(args, context)`。

## 三、逐层深度分析

### 3.1 第一层：Bash 解析器（12,306 行）— 理解命令在做什么

**这不是一个简单的正则匹配器，而是一个完整的 TypeScript Bash 编译器。**

- `bashParser.ts`（131KB）：纯 TS 实现，兼容 tree-sitter-bash AST 标准。50ms 超时 + 50,000 节点硬上限防恶意输入
- `ast.ts`（112KB）：FAIL-CLOSED 安全分析。用显式 allowlist 遍历 AST 节点，任何未识别的结构 → `too-complex` → 强制走用户权限确认
- `commands.ts`（51KB）：命令识别与危险模式分类
- `heredoc.ts`（31KB）：Here-document 解析，测试套件含 3,449 输入的 golden corpus

**设计哲学**：不是"识别危险命令然后拦截"，而是"理解不了的命令就不假设它是安全的"。

```
输入: VAR=val git push && $(echo npm) test
AST:  ├── 环境变量赋值: VAR=val       → 识别，安全
      ├── 子命令1: git push           → 识别，匹配规则
      ├── 操作符: &&                  → 识别
      └── 子命令2: $(echo npm) test   → 命令替换 → too-complex → 弹确认
```

**一个极端案例**：`rm -rf /` 是危险的，但 `RM='rm -rf'; FLAG='/'; $RM $FLAG` 也危险。正则只能拦截前者，AST 可以追踪到后者的变量展开。而 `too-complex` 策略意味着——即使 AST 没完全追踪到，也不假设安全。

### 3.2 第二层：权限引擎（9,409 行）— 决定允不允许

**14 步管线**不是一锤子买卖，而是一个层层递进的决策树：

```
1. 是否为只读工具？                → 是 → allow
2. 是否为已知安全模式？            → 是 → allow
3. 用户是否在 YOLO 模式？          → 是 → allow（跳过后续）
4. 是否有 MDM 强制 deny 规则？    → 是 → deny
5. 是否有用户设置的 deny 规则？    → 是 → deny
6. 是否有 MDM 强制 allow 规则？    → 是 → allow
7. 是否有用户设置的 allow 规则？    → 是 → allow
8. 是否为高风险操作？              → 是 → ask
9. Haiku 分类器预判？             → 安全 → allow
10. Haiku 分类器预判？             → 危险 → deny
11. 需要用户确认？                 → 是 → ask
12. 是否超时未回复？               → 是 → deny
13. 默认策略                       → ask
14. 记录决策日志
```

关键设计：
- **deny 优先于 allow**：即使有 `Bash(*)` → allow 的通配规则，`Bash(rm -rf /)` → deny 优先命中
- **规则粒度是子命令级**：`Bash(git push)` 和 `Bash(git rebase)` 可以有不同的权限
- **来源分层**：MDM（企业强制）> 用户设置 > 项目设置 > 默认

### 3.3 第三层：沙箱（~1,000 行 + 闭源运行时）— 做了也被关着

核心原理：**不是 Docker，是"一次性包装纸"**。每条 Bash 命令外面包一层内核级隔离，命令结束沙箱即毁。

```
Linux + Bubblewrap:
bwrap \
  --ro-bind /usr /usr \              # 系统库只读
  --bind /home/user/project /home/user/project \  # 项目目录可写
  --tmpfs /tmp \                     # 临时文件隔离
  --unshare-all \                    # 隔离所有命名空间
  --unshare-net \                    # 无网络
  bash -c "your command"

macOS + Seatbelt:
sandbox-exec -f /tmp/profile.sb \    # .sb 配置：Scheme 风格 DSL
  bash -c "your command"
```

启动时间 < 10ms（对比 Docker 的 500ms+），所以能做到每条命令包一次。

**沙箱的文件系统是白名单模式**：默认什么都看不到，明确列出允许的目录。不是"禁止访问 .ssh"，而是"除了项目目录和系统库，什么都看不到"。

### 3.4 第四层：Hooks（3,721 行）— 人类定规则

12 种事件类型：PreToolUse / PostToolUse / Notification / SessionStart / Stop / PreCompact / PostCompact / 等。

Hook 可以执行任意 shell 命令，非零退出码 = 拦截工具调用。支持匹配模式、环境变量注入、超时控制。

## 四、my-coder 对比：我们砍掉了什么

| 安全层 | Claude Code | my-coder (当前) | 为什么砍 |
|--------|------------|-----------------|----------|
| **Bash 解析** | 12,306 行 TS AST 编译器 | 7 个危险命令正则 | 单用户不会恶意构造命令绕过自己 |
| **权限引擎** | 9,409 行，14 步管线 | 无（全部 allow） | 自己用不需要询问自己 |
| **沙箱** | ~1,000 行 + 闭源运行时 | 无 | 个人开发机不需要隔离自己的命令 |
| **Hooks** | 3,721 行，12 种事件 | 无 | 手动跑测试不比配 Hook 麻烦 |
| **Haiku 分类器** | 每次工具调用前预判 | 无 | 单人不需要 AI 帮你判断安全 |
| **总计** | **~26,500 行** | **~20 行（7个正则）** | **缩减 99.9%** |

### 我们保留了的安全机制

1. **7 个危险命令正则**（BashTool）：`rm -rf /`、`rm -rf ~`、`>/dev/sd*`、`mkfs.*`、`dd if=...of=/dev/`、fork bomb、`chmod 777 /`
2. **Phase 46 自保机制**（+40 行）：pkill/killall 拦截、自 PID 感知、自引用检测
3. **原子写入**（FileWrite/Edit）：tmp + rename，防止写坏文件
4. **路径边界**（隐式）：Edit 的 old_string 必须精确匹配，防止误改

### 远期升级路径

已规划但未实施（详见 [[security-system-plan]]）：

```
Phase S1: 规则层 (~300行) — allow/deny/ask + 通配符匹配
Phase S2: 语法层 (~500行) — tree-sitter AST + FAIL-CLOSED
Phase S3: 行为层 (~200行) — Pre/PostToolUse Hooks
Phase S4: 隔离层 (~200行) — Bubblewrap/Seatbelt 命令行包装
```

## 五、核心洞察

### 5.1 "手要厚"的真正含义

Claude Code 源码分析里有一句话："大脑要薄，手要厚，底座要稳。" 之前理解为"工具要完善，能应对各种场景"。深入看完工具层代码后，更精确的理解是：

> **"手要厚"不是说工具功能多，而是说每个工具外面包了足够厚的安全层。工具逻辑本身很薄——真正占代码量的是"判断能不能做"和"防止做坏事"。**

BashTool 的 12,411 行里，真正 `execSync(command)` 的那几行不到 100 行。其余 12,300 行全部是安全基础设施。

### 5.2 安全代码的三个来源

Claude Code 的安全代码来自三个不同的需求，只有第一个与"AI Agent"有关：

1. **AI Agent 特有的**：Haiku 分类器（AI 预判 AI 的工具调用是否安全）、Agent 权限继承
2. **多用户 SaaS 产品的**：MDM 远程管理、4 层配置继承、企业 SSO、审计日志
3. **通用命令安全的**：Bash AST 解析、沙箱、Hooks、危险模式检测

对于单人使用的 my-coder，第二类完全不需要，第一类也不需要（因为用户就是操作者本人），第三类可以大幅简化（7 个正则 + 自保机制 = 够用）。

### 5.3 安全是"给别人用的"代码

Claude Code 的 ~26,500 行安全代码中，至少 60% 是为了"让不认识的人也能安全使用"——企业部署场景下，管理员不知道终端用户会输入什么命令。当用户 = 操作者本人时，这些安全层就变成了"自己拦自己"。

**但这不代表单人 Agent 不需要安全。** Phase 46 的自保机制就是反例——Agent 执行 `pkill -f "dist/main.js"` 清理残留进程，把自己杀了。这不是"恶意用户"，而是"AI 不知道自己就是那个进程"。单人场景的安全问题不是"防坏人"，而是"防 AI 的盲区"。

### 5.4 一个反直觉的事实

> **Claude Code 里"安全"的代码量 > "智能"的代码量。**

- 核心 Agent 循环（QueryEngine.ts）：1,295 行
- Bash 安全解析器（bash/）：12,306 行
- 权限引擎（permissions/）：9,409 行

大脑 1,295 行，而仅 Bash 的安全外壳就 12,306 行——**安全代码是智能核心的 10 倍。** 这不是设计缺陷，这是生产级系统的必然代价。但反过来也说明了——如果你不需要这些安全层，Agent 的核心逻辑其实非常简洁。my-coder 的 1,800 行就是证明。
