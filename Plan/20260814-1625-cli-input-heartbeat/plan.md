# 设计方案

## 改动一：降渲染心跳频率

### 现状（实测）

| 定时器 | 文件:行 | 间隔 | 频率 |
|--------|---------|------|------|
| `thinking_tick` 心跳 | query_loop.ts:175 | 100ms | 10Hz |
| 工具 `toolTick` 心跳 | query_loop.ts:105 | 100ms | 10Hz |
| `pollEvents` 渲染轮询 | progress.ts:42 | 80ms | 12.5Hz |
| `drainTimer`（IME drain） | cli.ts:125 | 100ms | 10Hz |

### 目标

渲染频率 1Hz，对齐 Claude Code。

### 改动点

| 定时器 | 改法 | 理由 |
|--------|------|------|
| `thinking_tick` 心跳 | 100ms → 1000ms | 秒数 1s 一跳足够，10Hz 无意义 |
| `toolTick` 心跳 | 100ms → 1000ms | 同上 |
| `pollEvents` 轮询 | 80ms → 1000ms | 消费端节奏与生产端对齐 |
| `drainTimer` | 100ms → 500ms 或保留 | IME drain 非渲染，可单独评估 |

### 关键决策：tick 合并逻辑不变

`pollEvents` 里已有 tick 合并（每轮只渲染最后一条 tick）。降到 1Hz 后，这个逻辑依然成立——只是从"80ms 合并一次"变成"1s 合并一次"。渲染输出更少，效果相同。

### 秒数显示影响

- 现在：`Thinking (2.6s)` 每 0.1s 跳一次
- 改后：`Thinking (3s)` 每 1s 跳一次
- **体验无损**：思考阶段通常持续数秒，1s 精度完全够用。工具执行更短，心跳本就显示不出来。

## 改动二：自建内容管理（治本输入层）

### 历史经验（Notion：豆包输入法崩溃修复）

之前「豆包输入法导致 Terminal 崩溃」的诊断结论是五层问题叠加，其中**输入端只做了绥靖**：

- 输出端：term-wrap 折行 → **真正治本**
- 输入端：「输入截断 500 字符」防御 IME memmove bug → **绥靖，且当前代码里已丢失**

当时明确记录：豆包语音大量输入 → IME `insertText` → `memmove` 越界 → SIGBUS（Apple Terminal bug）。当时的对策是截断输入量，**不是解决"大量输入"**。现在要支持一行几万字 + 粘贴几万行，绥靖方案失效，需要治本。

### 现状：readline 的「单行 + 行编辑」模型，两大致命限制

```ts
rl.on('line', (line) => {
  if (resolveLine) { resolveLine(line.trim()); resolveLine = null; }
});
```

- **限制 1（多行）**：`line` 事件按 `\n` 触发。粘贴几万行 = 触发几万次 line，只 resolve 第一行，丢 99.99%。
- **限制 2（超长单行）**：`createInterface({ input, output })` 默认 `terminal: true`，进入 raw mode 逐字符处理 + 回显重绘。一行几万个字 = 每字符重绘整行几万字 = O(n²) 卡死。即使粘贴，readline 内部仍逐字符走 `_ttyWrite` + `_refreshLine`。

### 治本方案：自建内容管理（自管 stdin 累积）

核心洞察：**readline 的「逐字符回显 + 行编辑」是大量输入时卡死/崩溃的放大器。自管 stdin = 原始字节流直接累积进 buffer，O(n) 纯累积，无回显重绘，大幅减少对 Terminal SwiftUI 渲染层的刺激。**

方向：不再依赖 readline 的 `line` 事件做输入边界，改为自己管理 stdin 字节流，累积成一个 buffer，用**显式边界**判定一次输入结束。

### Step 0 探测结论（已完成）

实测 mac 原生 Terminal：

1. **不发 bracketed paste 序列**（`ESC[200~`/`ESC[201~`），readline 也拿不到 → 方案 A 不可行
2. **粘贴多行确实触发多次 line 事件**（粘贴 3 行 → 4 个 line 事件，还夹空行）→ 证实 readline 单行模型会丢行

### 输入边界规则（用户确认）

不依赖 bracketed paste，用以下两个条件判定"一次输入结束"（满足任一即结束）：

1. **连续两次 `\n`**（出现空行）→ 输入结束
2. **`\n` 后无文本**（单行输入回车后就停，或多行粘贴的最后一个 `\n` 后无后续字节）→ 输入结束

实现上，第 2 条需要"输入安静期"（debounce）：收到 `\n` 后短暂窗口（50-100ms）内无新字节，判定结束。

### 候选实现

| 方案 | 做法 | 超长单行 | 多行粘贴 | 行编辑 | 工作量 |
|------|------|---------|---------|--------|--------|
| A. bracketed paste | ❌ 已排除（mac Terminal 不发序列） | — | — | — | — |
| B. 自管 stdin | 直接 `process.stdin` 累积原始字节，`\n\n` 或 `\n` 后无文本判边界 | ✅ | ✅ | ❌ 需自实现 | 大 |
| C. 混合 | 短输入 readline，大输入切 raw | ✅ | ✅ | ✅ | 中大 |

### 倾向（方案 B，自管 stdin 治本）

**B 作为治本主方案**：用户核心诉求是"一行几万字 + 粘贴几万行不崩溃"，自管 stdin 彻底绕开 readline 的逐字符回显重绘（O(n²) 卡死的根源），是唯一真正治本的路。

**行编辑做完善**（用户要求"尽量输入做得完善"）：自管 stdin 后，实现最小但够用的行编辑：

- ✅ 退格（Backspace）
- ✅ 回车提交（`\n` 结束）
- ✅ Ctrl+C 取消
- ✅ Ctrl+D（EOF）兜底结束
- ⚠️ 方向键历史（可选，用独立最小实现补回）

AI coding agent 的输入场景是"打字问问题 + 粘贴大段代码"，完整 readline 行编辑（Tab 补全、kill/yank、多行编辑）是次要的，**大输入接收能力 + 不崩溃才是核心**。

### 输入要覆盖的完整场景（完善清单）

1. 短输入：单行打字 + 回车
2. 超长单行：一行几万字，O(n) 累积，无逐字符回显重绘
3. 多行粘贴：几万行，`\n\n` 或 `\n` 后无文本判边界
4. 中文 IME 输入法：豆包等，大量输入不崩溃（历史 SIGBUS 教训）
5. 基础行编辑：退格、回车、Ctrl+C、Ctrl+D

## 改动三：输出折行完善

### 澄清：Notion 里的"30 行"是代码行数，不是折行上限

历史方案「term-wrap 折行（30 行 monkey-patch）」的 30 行 = **实现代码只有 30 行**，强调极简。折行本身**无上限**——`breakLine` 循环处理，任意长行都能按终端宽度无限折行。

### 现状缺口

历史方案是 monkey-patch 全局 `stdout/stderr`（所有输出自动折行）。后来重构移除了 monkey-patch，改成 `safeWrite()` 显式调用，但**现在只在 `renderResult`（最终结果）里调用**。

进度渲染（`thinking_start`/`tick`/`end`/`thought`/`tool_display`）走 `trunc` 截断，不是折行。当前是安全的（截断比折行更不会超宽），但折行能力只覆盖了一条路径。

### 完善目标

- 确认 `breakLine` 对任意长行（含几万字超长行、宽表格、长代码行）都能正确折行，无上限、不崩
- 审视是否所有可能产生超长行的输出路径都受保护（renderResult 用 safeWrite，进度渲染用 trunc 截断到 cols 宽度）
- 若 LLM 最终结果里含超长单行，`safeWrite` 的折行是否足够（当前 `breakLine` 已实现 ANSI SGR 栈重注入）

### 结论

折行逻辑本身已够健壮，本次主要**验证 + 补测**，而非重写。重点是确认「折行无上限」这个能力在超长行场景下真的不崩。

## 数据流变化

```
改前：
stdin 粘贴 5 行 → readline 触发 5 次 line → resolve 第一行，丢 4 行

改后：
stdin 累积原始字节 → \n\n 或 \n 后无文本判边界 → resolve 完整多行文本
（超长单行：O(n) 累积到底，不逐字符回显重绘）
```

## 不做的事

- ❌ 不重写整个渲染引擎
- ❌ 不改 Terminal.app（系统 bug，改不了）
- ❌ 不引入 iTerm2 等第三方依赖

## 验证方案

1. `npx tsc --noEmit` 零错误
2. 心跳：跑一个任务，观察秒数是否 1s 一跳，主屏是否还流畅
3. 多行粘贴：粘贴 5 行 + 粘贴几万行，确认是否完整接收
4. 超长单行：一行几万字，不卡不崩不丢
5. 中文 IME：豆包输入法大量输入，不崩溃
6. 折行：LLM 输出超长行/宽表格，确认折行无上限、不崩
7. Terminal 崩溃：长时间高频使用，观察崩溃是否减少
8. 记录现象到 observations.md
