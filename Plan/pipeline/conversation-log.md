## 用户提问

"我想问一下，我们的这个Agent.ts里面啊，在Agent引擎中，它把大模型的Call封装了，为什么没有封装Tool Use呢？就是没有把那个Tool也封装进去。那个大模型引擎，就是Agent引擎类里面，应该是封装了很多，就是主Agent和子Agent的注册表，这些都封装了，对吧？然后提示词也封装了，并且把大模型调用也封装了，为什么没有封装Tool这部分？是因为Run这个循环，那里面封装了Tool，所以Engine里面没有必要封装，是吗？这个在代码上是可以实现的，在逻辑上我不知道是不是自洽的。这个claude是怎么做的？它的设计是怎么样的？"

## AI 回复

分析了当前 Mycoder 的架构——tool use 在 run() 和 runSubAgent() 里重复了两遍，因为主 Agent 和子 Agent 的细节差异（显示事件 vs agentLoop 统计）让提取变得稍微不自然。对比了 Claude Code：Claude Code 的 QueryEngine 也是内联模式，没有抽出独立的 executeTool 方法，但它的每个工具自带权限/校验/渲染全套生存技能。

## 用户追问

"先别做，先聊清楚claude code是怎么设计的？它的设计方式有什么好处和坏处？"

## AI 深入分析

- Claude Code 是**纵向安全管道**（权限→沙箱→执行→记录），管的是"安全"
- 每个工具是独立公民：带 call()、checkPermissions()、validateInput()、render()
- 好处：工具完全解耦、可独立测试、适合大团队
- 坏处：每个工具代码量大、流程分散在多个文件、过度设计不适合单人

## 用户提出核心想法

"我的目的是为了让这个大模型能够良好地组织起来去活动。从这个角度来说，是不是应该学习一下管道？管道是什么样的一个组织逻辑？按我刚刚的想象，我觉得管道是可以让我把大模型的这个输入输出，以及工具的调用，以及子Agent的组织，变成一个平等的三个对象，是吧？"

## AI 确认并设计

管道模式把 LLM 调用、工具执行、子 Agent 编排变成三个**平等的水平环节**：

```
Think Stage（LLM）     → 输入→思考
Act Stage（工具）       → 思考→行动
Orchestrate Stage（编排）→ 管理子Agent/通知
```

三个环节共享同一个"公文包"（AgentContext），run() 只知道轮流转，不知道每个环节内部怎么工作。Claude Code 的管道是纵向安全控制，Mycoder 需要的管道是横向任务推进——方向完全不同。
